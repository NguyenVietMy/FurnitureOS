# Saved Designs and account recovery

Generation and fixture preview require no signup. Save sends only the selected server session ID, expected mutation version, explicit retention consent, policy version and an idempotency key. FastAPI obtains the authoritative current Design, including accepted Swap/Nudge changes. The browser cannot supply Room, Product, owner or Capture authority.

The `/saved` view lists the current account's saves, supports bounded pagination and opens `/saved/:id` directly. Restoring validates the archive and creates a fresh private mutation session. The original session is never revived. Same-session/version saves reuse a pending key after network ambiguity; pending hints contain no Auth tokens, expire after 24 hours and are never automatically retried with a new key. The durable list also recovers committed saves without hints.

## Retention and deletion

Save consent retains the Design's Room Shell, Placement Intents, fixed Placements, Room Type, Catalogue version, clearance width, original Zones, SearchReport and bounded ArrangementHistory. Generation history describes the original solve. Restore reconstructs Products from the exact Catalogue version and recomputes metre-based fits and circulation for the fixed Placements. Schema v1 uses normalized Pydantic JSON, sorted keys, compact separators, UTF-8, `ensure_ascii=False`, `allow_nan=False`, and SHA256. JSONB round trips normalize through the same model. An unknown schema, changed Catalogue/Zone derivation, invalid references, extra fields or digest/geometry corruption produces an explicit failure with no Design/session.

Captured saves retain only the original Capture UUID, confirmed revision and Room hash alongside the confirmed Room and Room Type. They retain no photos, Storage URLs/keys, photo analysis, calibrations, user email, Auth token, session, certificate or operation lease. Original photos/drafts still expire after creation plus 24 hours. Deleting or cleaning the original Capture revokes live-Capture sessions while saved copies and their own sessions survive. Deleting a save erases its payload/digest/raw source identifiers and revokes its restored sessions across processes; it never deletes an original Capture or other save.

A deleted receipt retains only owner ID, save ID, idempotency key, request-identity SHA256 and creation/deletion/removal-eligibility timestamps. Its protected retry horizon is 25 hours. After that horizon it becomes eligible for lazy removal during that owner's next new save; it can remain physically stored longer if the owner does not save again. There is no scheduled physical marker-removal deadline. Matching stale POSTs return `deleted`/410 while the marker remains; mismatches return conflict. DELETE is repeatable, including after marker removal. New creation serializes on the owner and removes only eligible tombstones. Existing retries and deletion work at quota. Limits are 100 active saves, 100 creations per rolling hour including later deletions, 3100 active receipts/unexpired tombstones per owner, 256 KiB normalized snapshots, 32 KiB HTTP save bodies and 25 records per list page. Source-session admission is capped at 30 minutes even with a custom store TTL.

## Identity

The installed Supabase JS 2.117.3 adapter uses `updateUser({email})`, `verifyOtp({email,token,type:'email_change'})`, `refreshSession()` and a current `getUser()` check before reporting same-UUID linking complete. An existing-account conflict preserves the current anonymous account and saves. Automatic merges and OAuth are outside this flow. Returning email OTP uses `signInWithOtp({email,options:{shouldCreateUser:false}})` and a deliberate account-switch choice. Email changes and sign-in require working hosted delivery/templates/configuration; none are configured by this change.

SDK persistence is the only Auth token store. Account/token transitions abort private work. Same-owner refresh/linking preserves Capture recovery pointers; signout/different UUID clears private previews and previous-owner recovery pointers. API authorization validates the token with Auth and requires its exact top-level UUID/anonymity claims to agree with the current Auth user. SQL repeats the current signed-claim agreement. The legacy SQL function name `capture_anonymous_owner` deliberately now admits both current anonymous and permanent owners. Owner predicates and restrictive Storage SELECT denial remain in force.

Sources: [anonymous identity linking](https://supabase.com/docs/guides/auth/auth-anonymous), [updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp), and pinned `node_modules/@supabase/auth-js/src/GoTrueClient.ts`. The reviewed 2026-10-27 changelog's obsolete-client CBC TLS change and extension-specific PostgreSQL changes do not require environment upgrades for this ticket.

The shared Auth authority guards the pinned SDK through its supported fetch and storage options. Owner changes, signout and initiating-view cancellation abort obsolete Auth requests. Complete responses are checked before the SDK sees them, and synchronous writes to its existing session key repeat the operation/owner/token check. Notifications must match that persisted session before either Capture or saved views accept them. Bounded in-memory response admissions are consumed by SDK writes; they never persist tokens or authorize application requests. No second token store, SDK patch, or dependency is introduced. Cancelling a delivered verification cannot undo a change already accepted by the external Auth service; the unchanged current SDK owner remains authoritative and may need an explicit refresh when returning.

## Activation and proof

Saved features default closed. They require `FURNITUREOS_SAVED_ENABLED=1`, `FURNITUREOS_SAVED_AUTH_VERIFIED=1`, `FURNITUREOS_SAVED_SCHEMA_VERIFIED=1` and the existing server Supabase URL/public/secret configuration. These are deployment attestations: set them only after the corresponding real environment checks. Capture upload/Storage/cleanup/server-photo attestations remain separate. Reading/listing/restoring/mutating an owned saved copy never requires Capture upload or photo activation. Creating a save from a live Capture still requires its existing configured Capture authority.

The additive migration `20261027184021_saved_design_ownership.sql` was created using version-checked Supabase CLI 2.122.0 `migration new`. Existing migration bytes remain unchanged. All new tables have RLS; direct mutation is denied. Definer RPCs have empty search paths and explicit grants: caller JWT reads/deletion and a narrow service-only creation RPC. Owner, current Auth row and source row locks establish commit order for source deletion versus save. Storage remains server-only.

Capture, operation-lease and source-session liveness use actual database wall time after lock waits and again in the insertion statement. Session expiry is trusted transient commit metadata, excluded from the stored archive. Creation timestamps, rolling-hour quotas and the deletion marker horizon likewise use wall time, so transaction-start time cannot extend authority or shorten retention after a lock wait.

Local proof uses `supabase/tests/bootstrap_local.sql`, the complete ordered migration chain and all SQL contract scripts on disposable PostgreSQL 17. `backend_tests/test_saved_designs.py` and `test_saved_sql_races.py` use real RPC/policies with controlled external Auth/Storage, including concurrent connections and restart recovery. Set `LOCAL_TEST_POSTGRES_PORT` only for an explicitly disposable local `ticket15` database with the complete chain installed; these tests skip when that local configuration is absent. The controlled production-build browser harness is external to the worktree. No test parameter or production HTTP endpoint enables that harness.

Controlled proof is not hosted Auth/email delivery/configuration, deployed RLS/Storage, or hosted session-recovery acceptance. Those gates remain UNRUN. Paid room-photo/vision/provider quality/timing/cache gates remain deferred to end of project; physical-phone/manual calibration is waived, not passed. Open issue #9 remains an external tracker gate.
