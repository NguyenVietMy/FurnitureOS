## Ownership and lifecycle

The browser obtains a real Supabase anonymous authenticated session before creating a Capture. Restored and newly created SDK sessions must have `session.user.is_anonymous === true`. FastAPI verifies the access token with the configured `/auth/v1/user` and requires its server-owned `is_anonymous` boolean to be exactly true; it never trusts a submitted owner ID or mutable user metadata. Direct authenticated Data API/RPC access requires both the signed top-level `auth.jwt().is_anonymous` boolean and the current `auth.users.is_anonymous` identity. The latter prevents an old anonymous token from granting private access after the account becomes permanent. Account linking is outside this feature: an existing permanent or missing-flag session is rejected without signing it out, converting it or deleting it. An Auth event losing anonymity clears private state and aborts late work even when the UUID is unchanged. See [Supabase anonymous users](https://supabase.com/docs/guides/auth/auth-anonymous) and [JWT fields](https://supabase.com/docs/guides/auth/jwt-fields).

Caller JWTs carry all Capture metadata reads and user RPCs. Photo GET and analysis use one narrow server-secret Storage fetch only after current anonymous Auth, caller-owned active Capture, exact revision, live operation lease and accepted manifest/hash checks. The server derives the canonical UUID key, uses only the exact configured project HTTPS root and a fresh internal UUID nonce, refuses redirects, and bounds transport to five seconds and 400,000 bytes. It rechecks identity, manifest and lease after hashing the returned canonical bytes; the API asserts authority again immediately before Response or provider submission. Failure emits no photo bytes or provider call. No generic privileged metadata lookup, URL signing, caller-supplied key/URL, Storage response headers, nonce or secret reaches the browser. API images remain no-store/nosniff. Direct anon/authenticated Storage SELECT is denied for the Capture bucket, even alongside a competing permissive policy. Server-only upload, analysis-result and confirmed-Room seams retain their authority checks; cleanup retains its existing service access. Nothing private is served with a publishable key alone. Captured Design sessions retain persisted owner/revision/Room-hash/expiry/lease checks; public fixture sessions retain their capability contract.

Creation requires explicit handling/retention consent at both HTTP and SQL boundaries. Captures expire **24 hours after creation**, irrespective of edits. Delete immediately tombstones access and revokes local sessions. Physical Storage removal happens in a durable job; metadata is purged only after every inventoried byte key is confirmed absent. Jobs run every 15 minutes, retry with bounded backoff, and enter attention-required after eight failures with daily retry. There is no guaranteed deletion latency. An expired/tombstoned Capture stays inaccessible while cleanup is delayed. Clearing anonymous browser credentials can lose access. Service deletion cannot remove provider copies or previously downloaded images.

Deletion polling is a separate lifecycle contract: only an owner-accessible, genuinely deleting row returns `{id, state: "deleting", inaccessible: true, cleanupStatus}`. Active and expired non-deleting rows return the same not-found response. The poll never includes draft, Room, photo or calibration data. It remains available while cleanup is pending; not-found after physical metadata purge completes the client deletion flow.

Only JPEG/PNG raw bodies up to 4,000,000 bytes are accepted. The decoder verifies actual format, performs a full decode, rejects animation/truncation/bombs and unsupported dimensions, rotates EXIF once, and emits a fresh metadata-free RGB JPEG. Originals are never persisted. Canonical JPEGs are at most 400,000 bytes and satisfy the installed single-image provider's visual envelope. Eight slots and lifetime 32 MB input reservation bound retries/removal churn. Four active Captures, four creations/hour, 32 ingestion attempts/hour, two concurrent owner operations, one owner upload/decode, one owner vision and process semaphores further bound work. JSON is limited to 32 KiB before buffering. Analysis is explicit, single-photo, semantics-only, maximum two attempts/photo and 16 attempts/Capture; it uses the existing local provider ledger, model and transport.

## Measurements and corrections

Wall A is user-chosen; B/C/D follow clockwise. Internal north/east/south/west identifiers are stable labels, not compass claims. At least four distinct accepted wall photos and explicit inventory review on every wall are required. Bedroom and rectangle are explicit declarations. Unsupported shapes return to selection without inventing a rectangular replacement. Missing dimensions and unknown Opening operation remain required-data blockers. Every Opening supports wall, type, distance from wall start, width, bottom/sill, height, clearance, hinge and swing corrections. Only confirmed inward 90-degree door swings are supported. Same-wall overlapping Opening areas and geometric bounds are rejected by the same authority during review, confirmation and generation.

A successful current semantic result atomically advances the Capture revision, returns it to draft, clears the validated Room/hash/confirmation and invalidates explicit inventory reviews for the photo's primary/observed/proposed walls. Unknown proposal walls require review of all walls. New present or unresolved furniture evidence also clears the empty-Room acknowledgment. Numeric corrections, corrected Openings, dimension evidence and final-dimension confirmation survive. Local derived sessions are revoked, and persisted final liveness checks reject remote or in-flight old results. The UI clears the solved scene and disables generation until the current evidence is explicitly reviewed and the Room reconfirmed. Old operation leases remain bounded and releasable after invalidation; they cannot block corrections to the new revision. A late analysis result cannot overwrite subsequent corrections.

Ordinary perspective photos have no recoverable metric scale from bounding boxes. Optional prefill uses a user-marked, flat **A4 sheet or measured rigid rectangle**, four ordered visible corners, and actual full dimension endpoints in the **same physical plane**, in a standard 1× perspective photo. Floor calibration supports width/depth; a separate flush-wall calibration supports ceiling height. The installed implementation solves a normalized pivoted homography without NumPy/OpenCV. Convexity, area/edge, conditioning, horizon and extrapolation bounds reject unsupported setups. Each endpoint/marker coordinate is perturbed ±2 canonical pixels, up to 50 solves for two segments. More than 5% sensitivity or any invalid probe returns typed-input-required. Sensitivity is not metric confidence; physical coplanarity, lens suitability and endpoint correctness remain owner assertions. This does not claim lens calibration or scene reconstruction.

Reference results are provisional, editable and source-linked. Existing typed values survive calculation. Fresh unsupported/absent reference fields stay blank. Opposite measurement conflict exceeding max(0.05 m, 5% of the smaller measurement) requires removal, remeasurement or an explicit override reason. Final dimensions always require user confirmation. Photo removal/reassociation invalidates dependent provisional evidence and inventory review. The warning explicitly says Detected Furniture is not reconstructed and the furnished Design assumes an empty Room.

The confirmed immutable Room reaches `generate_bedroom_for_room`; Catalogue selection, guidance, Zones, authoritative arrangement solving and circulation use that same Room. The old `generate_live_bedroom` fixture wrapper is preserved. Current scope is one required bed and optional rug. Invalid/unconfirmed Room and computationally unsupported Room are blocked before paid calls. Provider failure and valid no-fit are distinct. A bounded failure does not claim impossibility unless the solver's search is exhaustive. Captured Room guidance bypasses shared LRU caches.

The live helper binds FastAPI foreign/missing GET pairs to the exact intended API origin, paths, method and caller: signed B requires the fixed not-found 404 envelope; positively verified publishable-only without Authorization requires the exact authentication-required 401 envelope before lookup. Both safe bodies and bytes must match; extra fields, redirects, artifacts, request/caller mismatches and signed B 401 fail. This FastAPI pair rule is separate from Data API and Storage status checks. It requires HTTP 403/42501 for signed A/B Data API/RPC policy-denial proof. It also accepts the known HTTP 401/42501 only for an explicitly publishable-only caller whose exact API key has already succeeded in anonymous Auth, with no Authorization header and the exact intended valid request and payload. Signed A/B 401, invalid JWT/PGRST301/302, schema and constraint failures remain rejected. A Data API read/list may carry one relative Content-Location only when its literal table and once-decoded query exactly match the independently intended and actual request, allowing query reordering and a percent-encoded asterisk. Extra or duplicate parameters, mismatched filters/tables, schemes, authorities, credentials, fragments, redirects and signing artifacts fail. Storage header protections remain unchanged. The helper accepts the observed Storage upload/overwrite `400 / AccessDenied / Unauthorized / body 403` only in a valid Storage mutation context. An existing-key sign response `400 / NoSuchKey / not_found / body 404` proves no URL was issued only alongside immediate trusted verification of the original bytes and exact object identity. DELETE `200 []` is classified as a verified no-op only after the same immediate checks, never as a permission-coded error. Physical absence requires the exact validated NoSuchKey envelope plus a successful trusted Storage LIST confirming the exact filename absent; permission errors and generic 400/404 responses cannot prove deletion. Trusted evidence byte GETs require one fresh canonical UUID4 cacheNonce and the exact derived key, plus exact successful bounded LIST confirmation for presence/absence.
